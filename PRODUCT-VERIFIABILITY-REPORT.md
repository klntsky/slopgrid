# Product requirements worth formalizing

## Scope

This report includes requirements that describe relationships over typed data or state transitions: layouts, cells, histories, requests, budgets, jobs, accounts, and artifacts. It excludes fixed UI text, styling, static assets, lists of allowed options, and other requirements that can be checked by simple enumeration.

References point to [PRODUCT.md](PRODUCT.md), using section.item notation. For mixed clauses, only their data and transition rules are included, not their presentation details. Rows are property families, not counts of independently verified requirements.

**Doable:** yes for the application-owned rules below. **Compared with runtime assertions:** useful where several records, attempts, sessions, or failure steps must agree. A proof of an abstract protocol alone does not verify its database, network, or browser implementation.

### Conditional progress is a separate obligation

Eventual reconnection, fair worker service, and automatic recovery (6.1.2; 6.3.4; 9 items 1 and 4) are expressible over typed event traces, but not provable unconditionally. They need assumptions such as eventual network/storage recovery, available workers, and delivery of pending events. Model checking can expose protocol deadlocks; neither a proof nor a runtime assertion can force an unavailable external service to recover.

## C. Domain predicates better left to runtime checks

These still concern typed values, unlike excluded UI-copy assertions. They are straightforward to formalize, but a direct boundary check usually provides nearly the same practical protection at much lower cost.

| Requirement family                    | Product references  | Appropriate check                                                                                                                                                                        | Extra robustness from a dedicated proof                                                                                                                          |
| ------------------------------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Numeric and structural input validity | 3.1.5; 3.5.1; 3.7.2 | Require selected models where needed, finite positive text budgets, and positive whole-number custom dimensions. Keep invalid editable drafts representable; reject invalid submissions. | **Low:** use refined admitted types after checking untrusted input. Proving every comparison separately adds little.                                             |
| Upload acceptance                     | 3.7.8               | Check actual file type and byte length at the upload boundary.                                                                                                                           | **Low:** a theorem about a declared file record cannot establish that the received bytes match it.                                                               |
| Judge-result shape and score          | 5.6.1, 5.6.4        | Validate result count, boolean answers, and nonempty explanations; calculate matches against configured expected answers, including false.                                               | **Low to medium:** direct checks and property tests suffice for the local calculation. Durable association with the correct cell and attempt belongs in group B. |

## Priority and current coverage

Prioritize **semantic transformations and atomic edits**, then **whole-cell admission**, then **request/recovery protocols, authorization, and accounting**. Use ordinary assertions for group C. Geometry is a worthwhile later target if scroll synchronization continues changing.

The current F* proofs already cover independent ownership resolution, common-to-existing-case preservation, complete-uniform collapse, semantic transpose, and selected atomic-confirmation and request-ownership laws. They do not prove all of group A or any complete server/browser protocol in group B.

Formal proofs complement rather than replace runtime checks: untrusted data must still be checked, effects must implement the modeled transitions, and React/browser behavior must still be exercised end to end.
